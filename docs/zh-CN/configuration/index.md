# 配置是怎么回事

[English](../../en/configuration/index.md) | 简体中文

一个文件，严格 JSON，没有注释。这一页讲的是贯穿整份文件的规则，这样后面各个专
题页就能直接进入正题。

还没写过配置的话，先看[快速上手](../getting-started.md)，再回到这里。

## 文件就是全部接口

没有配置目录，没有 include，没有能覆盖某个字段的环境变量，也没有替你写文件的
命令。服务端只读一个文件，你在里面读到什么，它就做什么。

由此推出一句值得说明白的话：**服务端做的任何决定，只要不在文件里，就是从这台
机器推导出来的。** 没有藏在第二个文件或者编译进去的 profile 里。想看这些推导
值，随时 `rust-reality explain`。

## 严格，以及代价

解析器遇到看不懂的东西会拒绝，而不是忽略：

- 未知字段是错误，不是警告。拼错一个字段名，不会悄悄让某项设置失效。
- 未知枚举值是错误，并且报错会把存在的取值列出来。
- 重复的键是错误。JSON 允许重复，各家解析器都会悄悄留下其中一个；这里直接拒绝，
  因为读文件的人和解析器必须看到同一件事。
- 引用一个没声明的名字是错误，报错会列出声明过的名字。

代价是 JSON 没有注释，本项目宁可承担这个代价，也不引入第二套语法。要给部署写
说明，把笔记放在文件旁边，或者用用户上的 `label`——那是唯一一个纯粹给人看的
字段。

## 先定角色

第一个字段决定了它之后所有东西的形状：

```json
{ "role": "entry" }
```

- **`entry`**——公网节点。它终结跑在 REALITY 上的 VLESS（Vision flow），认证
  用户，并决定他们的流量去哪。
- **`landing`**——隐藏节点。它接收来自入口节点的一种内部协议，然后拨号目的地。
  它没有用户、没有 REALITY 身份、也没有路由，因为这些决定都不由它做。

属于另一个角色的字段会被指名拒绝。不存在两者兼有的配置，这是刻意的：把两者拆开
的全部意义，就是让一个可以被烧掉的公网 IP 远离干净的出口 IP，而一个进程同时扮
演两者会把这件事彻底抵消。

## 名字，以及它们从哪来

全篇会出现两种形状，用哪一种本身就说明了一些事情：

**按名字索引的对象**，名字本身就是身份：

```json
{
  "outbounds": {
    "landing-1": { "type": "nxr", "address": "10.0.0.2", "port": 7443, "psk": "..." }
  }
}
```

里面没有 `tag` 或 `name` 字段，因为键就是名字。两个出站不可能撞名，而引用一个
`landing-2` 会立刻失败，并把 `landing-1` 作为候选列出来。

**数组**，用在顺序或者数量本身有意义的地方：

```json
{ "routing": { "rules": [] }, "listeners": [], "users": [] }
```

路由规则是首个命中优先，所以它们的顺序是你在做的一个决定。监听器和用户是"若干
个东西"的列表，而不是"一个东西的若干种叫法"。

## `direct` 和 `block` 一直都在

每份配置都可以路由到两个从不声明的出站：

- **`direct`**——从这台机器拨号目的地。
- **`block`**——拒绝这个连接。

声明它们中的任何一个都是错误。它们不是协议，也没有什么可配的，所以让每份文件都
带上一行 `{"protocol": "blackhole", "tag": "block"}` 纯属仪式。
`rust-reality explain` 会把它们列进可用出站里，所以它们不会变成隐形行为。

## 你写的，和推导出来的

凡是有一个合理的、随机器而变的默认值的字段都是可选的，**不写它意味着"推导它"**，
不是"用一个固定常数"。

写了一个值，就是你把它钉住了。哪怕你写的值恰好等于推导会得到的值，也算钉住——
信号是"写了"，不是"不一样"。这一点在 `runtime.limits` 上很关键：`explain` 会把
每个值报成 `operator-pinned` 或 `startup-derived`，你写过的值无论内容如何都会
报成 pinned。

推论是：必须保持可见的决定是**必填**字段，而不是带默认值的可选字段。
`reality.cover`、`reality.privateKey`、`routing.default`，以及每个用户的 `id`
和 `shortIds` 之所以必填，正是这个原因——一份没写明这些的文件，本来就不该被
部署。

## 密钥就写在文件里

私钥和预共享密钥直接内联写。没有 keystore、没有密钥引用语法、也没有外部
provider，因为一个文件让热更新、备份和权限都保持简单，而一层密钥间接层本身也要
运维。

所以这个文件就是密钥：

```shell
sudo chown root:root /etc/rust-reality/config.json
sudo chmod 0600 /etc/rust-reality/config.json
```

密钥不会出现在日志里、`explain` 里或者任何报错里。关于密钥格式的诊断会显示
`[REDACTED]`，然后描述它违反了哪条规则。

## 规范形式

`rust-reality format` 会把文件改写成规范形式：校验过、缩进一致、键按参考手册记
载的顺序排列——出站排在引用它们的路由前面，必填字段排在可选字段前面。

```shell
rust-reality format -c config.json          # 打印
rust-reality format -c config.json --write  # 原地改写
```

它不是 `jq`。它先解析再校验，所以输出一定是这个二进制接受的文件；而 `jq .` 会
乐呵呵地把服务端拒绝的东西格式化得很漂亮，`jq -S` 则按字母排序，把相关的字段
拆得到处都是。

它从不自作主张。你写过的字段即使等于默认值也会留下，你没写的字段也永远不会被
展开进文件。格式化是幂等的，并且严格保持语义。

本套文档里每一段 JSON 示例都是规范形式，CI 会拿真正的解析器和格式化器逐个验证。

## 热更新：哪些热，哪些冷

`SIGHUP` 重载文件。大部分是热的：

| 热——重载即生效 | 冷——需要重启 |
| --- | --- |
| `users` | `role` |
| `routing` 和 `outbounds` | `listeners` |
| `dns` 服务器 | `network` |
| `log` 等级和目的地 | `runtime`（profile、tuning、limits、statusFile） |
| `assets` | `dns`（解析器策略） |
| 落地节点密钥，包括轮换 | |

这条线是结构性的，不是谁维护的一张清单：冷配置就是那些在第一个连接被接受之前，
每一个池、每一个上限、每一个 socket 都据以定尺寸的东西。改动其中之一的重载会被
拒绝，报错点名是哪一个，正在跑的配置继续服务。

活跃连接永远在它开始时的那一代上跑完。重载绝不会把已建立的会话挪到新的路由表上。
